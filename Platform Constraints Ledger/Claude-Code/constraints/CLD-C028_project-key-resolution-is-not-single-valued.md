**Constraint:** Project-key resolution in Claude Code is **not single-valued**. Three distinct resolvers coexist in one binary and disagree about the same inputs. `FF(e)` honours the `CLAUDE_CODE_PROJECT_DIR_NAME` override unconditionally; bare `KV(e)` ignores that override entirely and is the one selected whenever `CLAUDE_CODE_REMOTE_MEMORY_DIR` moves the memory base away from the config directory; and `ONe(e,t)` honours the override only **conjunctively**, when `CLAUDE_CONFIG_DIR` is set as well. The same environment therefore yields a different key depending on which code path asks. The harness ships `qRr(e)`, a function that returns the derived key only when it differs from the effective key, which is the implementation acknowledging the divergence rather than an inference about it. The underlying encoder is separately lossy in two ways: `$Do` collapses `/`, space, `_`, `.` and `-` all to a single `-`, so no decode is unique, and beyond 200 characters the key is truncated and suffixed with a base-36 hash that is not reproducible outside the process.

**Design consequence:** No tool, hook, script, audit or document may compute a project key once and treat it as authoritative, and none may decode a key back to a path by substitution. A design that assumes one key per path is invalid, not merely imprecise. Three specific failures follow. First, any instrument that reports "the" resolved store must state **which resolver it used**, because a bare path is unfalsifiable and a reader cannot tell a correct answer from a differently-derived one. Second, an orphan or liveness check built on a naive `-` to `/` decode will report live stores as orphaned and orphaned stores as live; both error directions were observed, and the false-orphan direction has now produced a wrong finding twice in this configuration, once against a live repo and once against a frozen clone. Third, because the store resolver memoizes on the composite `Va()|Aje()` rather than on the path, one process can legitimately hold one value while a differently-gated caller computes another, so "resolution is stable within a session" is not a safe premise either.

**Sanctioned workarounds:** Never decode a key; **enumerate** instead. Recover a path from a key with a separator-frontier search over the candidate separators `/`, space, `_`, `.` and `-`, testing each prefix against the filesystem, as implemented in `~/.claude/scripts/align-audit.sh` check 12; report a truncated frontier explicitly rather than silently capping it. When a key must be produced rather than read, apply `KV` (`path.replace(/[^a-zA-Z0-9]/g,"-")`, valid only while the result is at most 200 characters) and confirm the resulting directory exists before relying on it. Any hook or report that names a resolved store must also name the branch that produced it and must declare the branches it cannot observe, since a CLI or `--setting-sources` override is invisible from inside a hook. Re-verify the resolver set after every upgrade; three paths that already disagree are three paths that can drift apart further.
