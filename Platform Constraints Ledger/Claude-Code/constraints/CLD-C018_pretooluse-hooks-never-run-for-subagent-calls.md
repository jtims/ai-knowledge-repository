**Constraint:** `PreToolUse` hooks configured in user-scope `settings.json` do NOT run for tool calls issued by Agent-tool subagents. The permission layer (`permissions.allow` / `ask` / `deny`) and `PostToolUse` logging DO apply to subagent calls.

**Design consequence:** Every Change-Control mechanism implemented as a `PreToolUse` hook is absent inside subagents - here that is the whole protected-path scheme: `pre-write-gate.sh` (Edit/Write/NotebookEdit), `bash-write-tripwire.sh` (Bash), `machine-state-gate.sh`, `pre-push-gate.sh`, and both spawn-pin gates. Because the 8 patterns in `_protected-patterns.sh` have ZERO corresponding `Edit()`/`Read()` permission rules, a write-capable subagent can modify the synced skills folder, any synced-folder path, `.claude/hooks/`, `.claude/settings.json`, `.claude/context/`, `.claude/CLAUDE.md` and any `.env` with no gate and no prompt - including the hook scripts and settings that implement the governance itself. This INVERTS the closing conclusion of [[CLD-C013_file-permission-rules-only-edit-and-read]] ("the hook layer is the real enforcement here, not permission path-rules alone"): for subagents the hook layer does not exist, so the permission layer is the only enforcement available. Credential and shell-config paths are unaffected, being covered by the existing `Edit()` rules.

**Sanctioned workarounds:** (1) Express protected-path Change Control as `Edit(path)` permission rules, which per [[CLD-C013_file-permission-rules-only-edit-and-read]] cover Edit, Write, MultiEdit and NotebookEdit, and which DO apply to subagents, and which [[CLD-C019_ask-rules-fail-closed-without-an-answerer]] CONFIRMS as the correct lever for interactive use; see the now-resolved (6). (2) Strip Write/Edit/Bash from any subagent that does not need them via `tools`/`disallowedTools` - the only frontmatter lever that survives packaging per [[CLD-C009_plugin-subagents-ignore-permission-hooks-mcp]]. (3) Do NOT expect `Bash(...)` permission patterns to replace `bash-write-tripwire.sh`: the tripwire's write-shape regex has no permission-pattern equivalent, so shell-mediated writes by subagents remain partially ungated even after (1) and (2). (4) Never validate a subagent governance design by observing the main thread - the two dispatch paths differ, and a hook that demonstrably fires for the driver proves nothing about a subagent. (5) Scope note: plugin-level `hooks/hooks.json`, which [[CLD-C009_plugin-subagents-ignore-permission-hooks-mcp]] records as applying inside subagents, was NOT exercised by this probe, and whether the behaviour above is documented-by-design was not checked against the hooks doc - both remain UNKNOWN. (6) RESOLVED 2026-08-23 by the D-E probe (session 6), in the favourable direction. An unanswerable `ask` does NOT resolve like a `deny` for an in-session subagent. Although [[CLD-C002_subagents-never-receive-workflow-tool]] leaves a subagent with no `AskUserQuestion`, the PERMISSION LAYER is not bound by that: an ask-matched subagent tool call is surfaced to the owner through the PARENT session UI and resolved there. Evidence: a haiku-pinned `general-purpose` subagent edited two ask-matched decoys, both writes LANDED, at 6678ms and 6552ms against 316ms for a non-ask Edit by the same agent on an adjacent file, and the owner confirmed the same turn that prompts appeared and were approved. Workaround (1) is therefore CONFIRMED, not inverted, and the permission layer is a usable substitute for the PreToolUse hooks this constraint proves absent. The inverse case is recorded separately as [[CLD-C019_ask-rules-fail-closed-without-an-answerer]]: with NO answerer present, meaning headless `claude -p`, CI, or scheduled runs, the same rule fails closed and hard-blocks, and `acceptEdits` does not satisfy it. Acted on 2026-08-23: 7 `Edit()` ask rules were applied over the governance subset of `_protected-patterns.sh` and the two content patterns were deliberately excluded, on the reasoning that an ask over a path agents legitimately write to taxes the owner with a prompt per file. See the owner's config register v2.11, item D-E. (7) **OPEN QUESTION, do not treat this node as settled evidence for the settings.json case.** The official sub-agents doc states the opposite of this constraint, verbatim: *"Hooks from settings files, managed policy settings, and plugins all apply inside subagents, so a `PreToolUse` hook in `settings.json` also runs before every tool a subagent uses."* Most likely reconciliation is version skew between the doc and the installed harness, but that is ASSUMED, not verified. Two of this node's three evidence legs are also now weaker than they read: the record-differential leg is VOID as an instrument (see the 2026-08-23 session-7 provenance entry) and the permission-coverage leg has been overtaken by the 7 `Edit()` ask rules applied under workaround (1). **The timing-discriminator leg stands and is what the constraint now rests on - one leg, not three.** Owner ruling 2026-08-23: file as an open question, do NOT re-probe this session. Before any future design leans on this node, re-run the probe against the current harness version and use the CORRECT instrument, namely a `tool_result` with `is_error: true` whose content begins `PreToolUse:<Tool> hook error: [<hook path>]:` - subagent transcripts carry no attachments at all, so attachment-counting cannot work there. (8) **A PreToolUse hook declared in a SUBAGENT'S OWN FRONTMATTER *does* fire for that subagent - VERIFIED 2026-08-23 (session 7), headless leg.** This is a DIFFERENT mechanism from a settings.json hook and is not in tension with the constraint above. Probe: a temporary agent carrying `hooks: PreToolUse: [{matcher: Write, hooks: [{type: command, command: <script>}]}]` and `tools: Write` only; the hook denied via exit 2 on a uniquely-named path while an adjacent control write LANDED in the SAME invocation, delegation was confirmed structurally by exactly one subagent transcript, and the hook's own log recorded both the DENY and the ALLOW. Consequence: **per-agent frontmatter hooks are a viable mechanical bound where settings.json hooks are not** - this is the sanctioned route for the swarm `out_dir` problem. Residual: the INTERACTIVE leg was NOT run, because a newly written agent definition is not synchronously registered, so the in-session Agent-tool path remains unverified and may route differently. Do not treat (8) as covering the interactive case until that leg runs.
