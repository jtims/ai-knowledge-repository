**Constraint:** Surface: the claude.ai artifact runtime, viewed in the Claude Code desktop app's built-in browser pane. A published artifact page loaded at its claude.ai/artifact URL (observed on one artifact, the Cover Letter Desk; the frame layout belongs to the shared runtime, so the same for other artifacts is INFERRED) runs inside a sandboxed iframe served from a uuid-named `frame.claudeusercontent.com` origin, cross-origin to the claude.ai top document, so the pane's `read_page` (interactive filter), `find`, `get_page_text` and `javascript_tool` tools cannot see or reach the page's controls or text: `read_page` lists only the top banner's controls, `find` returns no match for the Analyze or hand-off controls, `get_page_text` returns only the banner text, and `javascript_tool` reads the frame's `contentDocument` as null; of the pane actions on record, only screen-level input through the `computer` tool (coordinate clicks, and typed text for the session 6 paste into step 0, whose exact action the records do not name) and screenshots reach the page.

**Design consequence:** Any design that has Claude enumerate an artifact page's controls, read its live DOM or text, or script it from the browser pane through `read_page`, `find`, `get_page_text` or `javascript_tool` is invalid when the artifact is loaded at its claude.ai/artifact URL; none of them reached a desk control there in the live probe, so scripted, DOM-level driving of a published artifact viewed that way is not possible with them. Behaviour inside the frame cannot be observed through those tools either: session 4 left the downloads handshake and the font fetch unexercised until the owner's first export. With the tools tested, live work against the page (pressing controls, capturing output, checking rendered text) becomes a coordinate-and-screenshot loop, and because a screenshot transcription is not a text extraction, any output reported as exact needs an independent check against a value the page itself computes (session 6 matched each transcription to the desk's word, sentence and longest-sentence meter, recomputed from the page code). Each in-page Claude call made this way spends the signed-in viewer's plan ([[CLD-CAP008_artifact-sample-capability-asks-claude-on-the-viewers-plan|CLD-CAP008]]); platform consent was already granted for this artifact in session 6 (WORKLOG line 128), and the per-run owner approval is a house rule of the owner project (its desk-test README), not a platform gate. Proven live against one artifact frame: all four tools on 2026-09-23; the earlier sightings, tool by tool, are itemized in the provenance. UNKNOWN: the Chrome extension's tools (`mcp__claude-in-chrome__*`) and the `form_input` tool were never tested against this frame in any session, so they are neither a confirmed alternate route nor a confirmed dead end. Two other routes were checked on 2026-09-23 in a second probe: loading the frame's own claudeusercontent.com URL as the top document returned a bare not found page (read_page empty, find no match, get_page_text not found), so the page is served only inside the parent document's frame and a direct load is not a route; postMessage from the top document was not exercised, and the desk's page source declares no message listener (searched for postMessage, addEventListener message and onmessage: none), so the page code offers nothing for a message to reach, while whether the runtime shell inside the frame listens is UNKNOWN.

**Sanctioned workarounds:** Drive the page by screen coordinates in the browser pane and read it from screenshots (session 6 proof runs; the 2026-09-23 probe confirmed only that the page renders and reads in a screenshot); narrow the viewport so the text reflows to one column before transcribing; verify every transcription against a value the page computes from its own code (the desk's meter, recomputed by a script in the owner project's desk-test folder, whose README holds the procedure) before treating it as exact; file inputs into the page through the artifact database with ArtifactData rather than through the DOM (the channel [[CLD-C031_artifact-page-network-is-blocked|CLD-C031]] names; [[CLD-C032_artifact-sample-call-exposes-model-tier-only|CLD-C032]] uses the same direction to hand named-model output to the page). Whether Claude Code can read back, through ArtifactData, rows the page itself writes to its database is not in this evidence: UNKNOWN. The page's own Download PDF, Download DOCX and Copy text controls are visible in the pane, but whether pressing them there delivers a file or text Claude Code can read is UNKNOWN (untested). The Artifact tool's own read returns the published source, not the live DOM, and was not tested as a substitute; the Chrome extension's tools and `form_input` stay UNKNOWN as above; loading the frame URL directly is ruled out, and postMessage has no listener in the page code.
