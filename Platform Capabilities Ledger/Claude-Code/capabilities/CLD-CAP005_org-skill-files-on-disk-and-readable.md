**Capability:** An org-managed claude.ai skill is **materialized on disk** at `/mnt/skills/organization/<skill-name>/`, and its **bundled `references/` files are readable by the model**, not just its `SKILL.md`. Progressive-disclosure multi-file skills therefore work on claude.ai, not only in Claude Code.

**What it unlocks:** A skill can be authored as a small always-loadable `SKILL.md` plus deep reference files, on **every** Claude surface. That keeps the trigger surface short while carrying arbitrary depth behind it, which is the only way a governance skill stays both loadable and complete. Without this capability a designer would reasonably assume that only `SKILL.md` survives an upload and would **collapse a multi-file skill into one monolith** to be safe, paying a large always-loaded cost for content that is needed on a minority of turns. That is precisely the wrong turn this node prevents: a five-file skill was one approval away from being flattened on the assumption that claude.ai could not reach `references/`, and the assumption was false.

**Caveats & linked constraints:** **Reachable is not loaded.** The decisive caveat is that nothing loads these files automatically. This is not an inference from a single failure: the two provenance entries above are a before-and-after on the same skill and surface differing only in the description, so the dependency of loading on description wording is **isolated and confirmed**, not merely plausible. Only the skill's `description` is in context by default, and a skill-search hit returns **metadata only** - finding a skill is not loading it. In the relayed session the model concluded the body was "unavailable" and reasoned from vendor tool schemas instead, producing a wrong answer on a polling field, until it was told the files were on disk. Two authoring consequences follow: a description must **instruct the model to open its own directory**, and it must not be so informative that partial answers feel sufficient, because a description that answers questions competes with the body instead of summoning it. Naming a bundled file by bare relative path in the description is actively harmful - it teaches that a dependency exists while implying it is out of reach. Distribution is still governed by [[CLD-C021_kb-edits-do-not-propagate-to-claude-ai-skills]]: a synced-folder or vault edit does **not** reach the claude.ai copy, so the on-disk copy is only as fresh as the last manual upload. Unverified adjacents, do not assume: the mount path for **personal** (non-org) skills, the behaviour on Claude Desktop and in Cowork, whether the path is stable across releases, and whether any per-file size or count limit applies at read time rather than at upload.
