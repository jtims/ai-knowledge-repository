**Capability:** A client paired as a device can read exactly how any document or folder is stored in the reMarkable cloud (its line in the root index, its own index, and its `.metadata` and `.content` JSON) from the current sync v3 root or from an older root named by hash, using blob downloads only, so the undocumented shapes that the vendor's own apps write can be learned from the owner's library without a single write.

**What it unlocks:** RMK-C004 closes the document API to this kind of client, so creating a folder or deleting an item has to be rebuilt on sync v3, and RMK-C003 makes every such write a rewrite of the account-wide root. The obvious ways to learn what a folder or a trashed item must look like are trial writes against that root, or trust in third-party source. This is the cheaper and safe path: read a folder the vendor app made, read an item the vendor app trashed, and, because superseded roots stay retrievable by hash, read the same item before and after a vendor-app action and compare the two. The write design then copies shapes the tablet is known to accept. It changed a build decision in this estate: `rr mkdir`, and `rr rm` as a move to the trash, are designed in detail only after `rr inspect` has read the shapes (an owner project rulings D37 and D38). It is also the way to record a full root hash before an experiment.

**Caveats & linked constraints:** Read-only is not the same as private: the output carries names and metadata from the owner's library, so it runs on the owner's word, on items the owner names, on the main thread. The shapes are undocumented and the vendor can change them. Three items were read, and that the fuller field set comes from the tablet touching an item was INFERRED from those three; a fourth weakens it, because the tablet trashed an 8-field folder and kept 8 fields. What a move to the trash changes is known for a move made on the tablet, of a notebook and of a folder (`parent` and `lastModified`); what the mobile, desktop and web apps write, and what a restore from the trash writes, are UNKNOWN. Whether trashing a folder rewrites its children is UNKNOWN: the one child read carried `parent: trash` itself, stamped 6.2 seconds before its folder. `rr inspect --root <hash>` has been exercised live once, on a root superseded 19 minutes earlier. How long the vendor keeps a superseded root is UNKNOWN beyond roughly an hour. Reading shapes does not make a write safe: any write built on them is still bound by [[RMK-C003_sync-v3-write-replaces-the-account-wide-root-index|RMK-C003]] (fail closed, re-emit verbatim, a planner with its own count rule, a dry run immediately before, a recorded previous root), and the document API stays refused ([[RMK-C004_document-api-returns-401-to-a-browser-paired-device-token|RMK-C004]]).
