## Reach-for quick sheet (the capabilities most likely to change a design)

- **[[CLD-CAP001_hooks-deterministic-governance|CLD-CAP001]]** hooks enforce deterministically — governance can live in code, not just advisory memory
- **[[CLD-CAP002_cross-scope-hooks-merge|CLD-CAP002]]** per-project SessionStart hooks merge with (don't suppress) global governance hooks — safe to decentralize per-project session automation
- **[[CLD-CAP003_automemorydirectory-redirects-store-from-subdir|CLD-CAP003]]** `autoMemoryDirectory` redirects a subdir's auto-memory store — per-project memory inside a shared vault, no git-init
- **[[CLD-CAP005_org-skill-files-on-disk-and-readable|CLD-CAP005]]** org claude.ai skills sit on disk with their `references/` READABLE — author small `SKILL.md` + deep references on every surface; but reachable is NOT auto-loaded, so the description must tell the model to open its own directory
- **[[CLD-CAP006_project-scope-settings-consulted-in-headless-and-sdk-runs|CLD-CAP006]]** a project-scope `autoMemoryDirectory` redirect is consulted in headless, print-mode and SDK runs unconditionally - the gate is `Aje() = !isInteractive() || trustAccepted`, and the non-interactive branch alone satisfies it, so automation does not need trust acceptance to get its own memory store. `userSettings` sits LAST in the chain, which is what makes a defensive user-scope pin safe to add alongside 21 project redirects. Settles precedence only: `--setting-sources` governs whether project settings are LOADED at all, upstream of this chain, and stays UNKNOWN
- **[[CLD-CAP007_skill-changes-load-live-without-restart|CLD-CAP007]]** a skill added or edited under `~/.claude/skills/` loads live in the running session, no restart - sequence skill work as install then verify in ONE session; live pickup is not validation (CLD-C001), and a top-level skills directory created mid-session still needs a restart
- **[[CLD-CAP008_artifact-sample-capability-asks-claude-on-the-viewers-plan|CLD-CAP008]]** a published artifact page can ask Claude on the viewer's own plan (text or JSON, page tools, images, cache, consent), so an agentic feature needs no backend and no API key
- **[[CLD-CAP009_browser-pane-drives-artifact-claude-call-on-the-owners-account|CLD-CAP009]]** Claude Code's built-in browser pane, when signed in to the owner's claude.ai (observed, not guaranteed; persistence UNKNOWN) and with the artifact's in-page consent standing, can drive that account's own private artifact by coordinates and screenshots, its in-page Claude call included, so an artifact build can be proof-run from inside a Claude Code session without a person operating the page; each run needs the owner's usage approval, read_page, find, get_page_text and javascript_tool reach no desk control in the frame (CLD-C033), and the Chrome extension's tools and form_input stay UNKNOWN
- **[[LOV-CAP001_external-integration-via-app-surface|LOV-CAP001]]** external systems CAN reach Lovable Cloud data via app-surface auth (edge-fn / PostgREST), despite no DB credentials
- **[[LOV-CAP002_publish-visibility-is-the-publish-posture-field|LOV-CAP002]]** `publish_visibility` — not `visibility` — is a Lovable project's public-vs-private publish posture; `visibility` is the editor state and never carries 'public', so a rule keyed on it never fires and fails silently

## Access mechanisms (live)

Pull-only, by ruling — **no `UserPromptSubmit` injection**:
1. This hub + each `<Platform>/_<Platform>-Capabilities-MOC.md`.
2. The `platform-constraints` skill carries a cross-pointer to this ledger (wired in Phase 4).

**Cross-ledger:** every capability node links to the constraint node(s) that bound it (see [[_SCHEMA-Capabilities]] → Cross-ledger rule). The two ledgers are one graph — a capability and its governing constraint are adjacent nodes.

**Owner roadmap:** shared validator/mirror generalization (Phase 2) · seed nodes (Phase 3) · skill cross-pointer + capture-protocol twin (Phase 4). The validator-location revisit is an open design question in the owner's working notes.
